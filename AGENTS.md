# Repository Guidelines

## Project Overview

`ovid-native` is the complete native implementation package for Ovid applications. It ships one PyO3 extension containing every supported Rust operation together with the Python models, tools, toolsets, and capabilities that adapt those operations to `ovid-core`.

This is deliberately one distribution. Do not split search, filesystem, AST, process, terminal, desktop, media, or future native operations into sibling Python distributions or platform leaf packages. Every published wheel contains the complete supported native surface. Python extras may add Python-only integrations, but they must not represent mutually different native binaries under the same distribution version.

`ovid-native` is optional from an application's perspective. `ovid-core` never depends on it. Applications choose whether to install it and explicitly select its tools or capabilities when constructing an agent. Installing this package must never change an agent implicitly.

## Architecture and Dependency Direction

The dependency direction is strict:

```text
Ovid applications
      | explicit activation
      v
 ovid-native
      |
      v
  ovid-core
      |
      v
 pydantic-ai
```

- `ovid-native` depends on the public contracts owned by `ovid-core`.
- `ovid-native` must never import `pydantic_ai` or provider SDK runtime types.
- `ovid-core` must never depend on or import `ovid-native`.
- Rust owns algorithms, native resources, platform behavior, concurrency, and cooperative cancellation.
- Python owns validated Ovid arguments and results, `BaseTool` and `BaseToolset` implementations, capability contributions, approval metadata, timeout policy, and error translation.
- Applications own agent definitions, prompts, permissions, activation, rendering, configuration discovery, and user-facing fallback policy.

Keep the PyO3 boundary narrow. Rust functions accept validated scalar values or purpose-built native values and return typed native results. Do not serialize through JSON merely to cross the Python/Rust boundary. Do not pass Pydantic models, Pydantic AI objects, agent contexts, or application services into Rust.

## Package and Version Contract

The Python distribution is `ovid-native`; the import package is `ovid_native`; the extension module is private `ovid_native._native`.

`ovid-native` follows semantic versioning independently from `ovid-core` and declares the supported core range in `pyproject.toml`. A core patch that preserves public contracts must not require rebuilding every native wheel. A breaking core tool or capability contract requires a corresponding native release and dependency-range update.

The native API version returned by `_native.runtime_info()` protects the private Python/Rust boundary. Increment it whenever the Python wrapper and compiled extension become mutually incompatible. It is not a replacement for the Python distribution version or the `ovid-core` compatibility range.

Keep the version in `pyproject.toml` and `Cargo.toml` identical for every release. `Cargo.lock` is committed and generated by Cargo; never hand-edit it.

## Key Directories

- `src/`: Rust implementation and PyO3 module registration.
- `python/ovid_native/`: typed Python boundary and Ovid integrations.
- `python/ovid_native/_native.pyi`: private native extension declarations maintained with the Rust exports.
- `tests/`: Python contract and installed-extension tests.
- `target/`: generated Rust and wheel build state; never edit or commit it.
- `dist/`: generated wheel and source distributions; never edit or commit them.

Organize Rust and Python modules by domain, not by language-level type or release phase. A search operation's Rust implementation, Python request/result models, tool, and capability should have obvious corresponding module names. Do not create generic `schemas`, `dto`, `interfaces`, `utils`, or `helpers` dumping grounds.

`python/ovid_native/__init__.py` remains empty. Consumers import symbols from the module that owns them. Do not define `__all__` or add package-level re-exports.

## Development Commands

Use uv, maturin, and Cargo from the repository root:

```bash
uv sync
uv run maturin develop
uv run task format
uv run task python-lint
uv run task type-lint
uv run task rust-lint
uv run task rust-tests
uv run task tests
uv run task build
```

`uv run maturin develop` installs the active native extension into the project environment. Run it after changing Rust exports and before Python tests that import `_native`.

The release build publishes wheels and one source distribution through maturin. A source distribution is supported behavior: it must contain every Rust source and workspace dependency needed to build without the repository checkout.

## Python Conventions

- Target current Python 3.14 conventions. The package is fully typed and includes `py.typed`.
- Ruff formatting is authoritative: 120-column lines, four-space indentation, single quotes, and sorted imports.
- Use `snake_case` for modules/functions/variables, `PascalCase` for types, and explicit names for native operations and tool factories.
- Annotate every function parameter and return type. Parameterize every generic; never use bare containers or `object` annotations. Prefer a precise type, otherwise use `Any`.
- Use Python 3.14 generic syntax. Do not introduce legacy `TypeVar` or `ParamSpec` declarations.
- Never silence ty or another type checker. Fix the type model or report the blocker.
- Prefer keyword arguments at call sites when passing multiple values.
- Use f-strings only for interpolation. Do not use `.format()`, `%` interpolation, or string concatenation for templating.
- Do not use local imports unless they are required to break an unavoidable import cycle. Resolve the cycle structurally first.
- All public structured DTOs inherit `ovid_core.models.BaseModel`; UUID-like root values inherit `BaseRootModel`. Do not repeat core model configuration.
- Use Pydantic models for validated values, not stateful services, native handles, factories, routers, or stores.
- Do not return unstructured dictionaries or lists of dictionaries from public functions. Represent complex public results with typed Pydantic models.
- Preserve direct validated field mapping at the PyO3 boundary. Avoid `model_dump()`, JSON serialization, and intermediate dictionaries when scalar or typed native arguments suffice.
- Keep imports free of native resource acquisition and environment-dependent side effects. Importing a module may load the extension but must not start threads, inspect workspaces, access credentials, spawn processes, or activate tools.
- Raise narrow typed exceptions and preserve causes. Never include secrets, command credentials, signed URLs, or sensitive file content in exceptions.
- Use async for filesystem, process, terminal, network, and other I/O exposed through tools. Never block the Python event loop.
- Functions should stay within 40 lines and files within 250 lines. Split by responsibility before exceeding either limit.
- Prefer guard clauses when the alternative exits. Separate logical groups with blank lines.
- Follow DRY strictly. Add an abstraction only when it removes demonstrated duplication or isolates the required Python/Rust boundary.
- Do not add comments, docstrings, or explanatory prose unless behavior is critical and genuinely non-obvious. Prefer clear names and smaller units.

## Rust Conventions

Target stable Rust with edition 2024. `rustfmt` and Clippy are authoritative. Unsafe Rust is forbidden unless a future operation cannot be implemented through a reviewed safe abstraction; changing that policy requires an explicit repository decision and the unsafe code must be isolated behind a narrow safe module.

### Generics and trait bounds

Write trait bounds in `where` clauses:

```rust
pub fn convert<T>(value: T) -> NativeValue
where
    T: Into<NativeValue>,
{
    value.into()
}
```

Use conventional generic names: `S` for streams, `Fut` for futures, and `F` for functions. Use `T: Into<Ty>` when callers are genuinely likely to supply multiple convertible types; do not add generic flexibility without a consumer.

### Public types and results

- Derive `Copy`, `Clone`, `Eq`, `PartialEq`, `Hash`, and `Debug` for public value types whenever their fields permit it.
- Derive `Default` only when the default has a clear semantic meaning.
- Mark side-effect-free functions `#[must_use]` when ignoring their result would make the call pointless.
- Prefer `Self` when referring to the type of the current `impl`.
- Avoid repeating the containing type's concept in field names. Prefer `Message { id }` to `Message { message_id }`.
- Expected operational failures return narrow Rust error types and become typed Python exceptions at the binding boundary. Do not panic for user input, platform failures, cancellation, missing files, process exits, or parse errors.
- Never use `unwrap`, `expect`, `todo!`, `unimplemented!`, or placeholder success values in runtime code.

### Strings, futures, and control flow

- Prefer `.to_owned()` when converting `&str` to `String`.
- Prefer `Box::pin(async { ... })` to `async { ... }.boxed()`.
- Use early returns when an absence or failure exits the function.
- Avoid `if let ... { ... } else { ... }`; use `match` when both variants produce behavior or a value.
- Use `=> (),` for intentionally empty match arms.
- Use full logging macro paths such as `tracing::debug!`; do not import macros solely to shorten the call.

### Modules, imports, and item order

Module declarations come first. Separate import groups with blank lines and use one `use` declaration per crate:

1. `std`
2. external crates and workspace crates
3. `crate`
4. parent/child modules only when a `crate::` path is not clearer
5. sparse re-exports after imports

When implementing `std::fmt` traits, import `std::fmt` and use `fmt::Display`, `fmt::Formatter`, and `fmt::Result`.

Order files for a first-time reader:

1. public types
2. public functions
3. private types
4. implementations and private helpers in top-down call order

Put the single non-private item before private implementation details. If public and private items are mixed, place public items first. Prefer `crate::module::Item` to `super::Item` or `self::module::Item`.

### Documentation

Documentation comments describe what an API guarantees, not how its implementation works. Use complete grammar and punctuation in prose. Short list items do not need ending punctuation. Link external contracts when useful. Write crate names verbatim rather than quoting or title-casing them.

Do not document private implementation that is clearer from its name and type. Public Python-facing behavior belongs in the Python models and tests unless Rust callers also consume the API.

## PyO3 Boundary Rules

- Use maturin as the only Python build backend.
- Keep the extension private as `ovid_native._native`; public consumers use typed Python modules.
- Update `_native.pyi` in the same change as every added, removed, or changed Rust export.
- The normal wheel uses PyO3's `abi3-py314` stable ABI. Do not use APIs that silently disable the promised wheel compatibility.
- Free-threaded CPython support is explicit. Every exported function and native handle must be thread-safe before declaring the module GIL-independent. Test 3.14t separately if it becomes a supported target.
- CPU-bound and blocking functions must release the GIL. Async functions must not retain borrowed Python values across await points.
- Cancellation is cooperative across the boundary. Long searches, traversals, parses, process waits, and stream operations must receive and check cancellation state.
- Keep Python object conversion at the edge. Perform bulk work in Rust and cross the boundary once per logical result or bounded stream item, not once per byte, match character, or AST node unless streaming is the contract.
- Do not expose raw pointers, Rust lifetimes, Tokio handles, Pydantic AI values, or provider SDK objects.
- Do not start worker pools while the dynamic loader lock may be held. Initialize runtimes lazily from an explicit operation if a subsystem needs them.
- Native code is trusted in-process code, not a sandbox. Filesystem, shell, process, desktop, and network operations must preserve Ovid approval and policy enforcement in their Python tool wrappers.

## Native Surface and Capability Policy

This distribution contains the complete native surface, but no agent receives all native tools automatically.

- Each operation is independently callable through an owning Python module.
- Related operations may form an explicit `BaseToolset`.
- Capabilities contribute tools or toolsets only when the application passes that capability to `AgentFactory`.
- Capability IDs and tool IDs are stable and namespaced under `ovid_native`.
- Duplicate IDs and implicit overrides are errors.
- Rust operations remain domain-neutral. Coding-agent concepts such as repository policy, agent roles, prompts, review workflow, and UI rendering stay in the consuming application.
- Platform availability is explicit and typed. Do not silently turn an unavailable native operation into a no-op or unrelated Python implementation.

## Packaging and Platform Policy

Publish standard wheels and one sdist; do not implement an import-time downloader or custom binary cache.

Initial wheel families are:

- Windows x86-64
- Linux manylinux x86-64 and ARM64
- macOS x86-64 and ARM64

Add musllinux or another architecture only with a supported consumer. Wheel tags do not encode x86-64 microarchitecture levels. Compile for a conservative baseline and use runtime CPU-feature dispatch inside Rust when an operation benefits from newer instructions.

Prefer pure-Rust dependencies. A dependency on a system shared library must include a wheel portability plan before landing. Every dependency affects all consumers because every wheel contains the complete native package.

Do not use Cargo feature combinations to publish different native surfaces under the same Python version. Features may control development and target-specific compilation only when the public operation set remains coherent and unavailable operations fail explicitly.

## Testing and QA

Python tests use pytest with 100% branch coverage for the Python integration layer. Rust behavior is covered by Rust unit or integration tests. Tests must defend observable contracts and fail on plausible bugs: boundaries, cancellation, platform availability, native error conversion, ordering, resource cleanup, and Python/Rust version compatibility.

Use the `mocker: MockerFixture` fixture for every Python test double, patch, spy, or environment mutation. Do not import `unittest.mock`, use pytest's `monkeypatch`, or introduce another mocking helper.

For each native operation:

- test the Rust success and failure behavior directly
- test the typed Python wrapper against the installed extension
- test cancellation and cleanup for long-running or resource-owning operations
- test unsupported-platform behavior where applicable
- execute a smoke scenario through the public Python API

Before reporting work complete, run:

```bash
uv run task type-lint
uv run task python-lint
uv run task rust-lint
uv run task rust-tests
uv run maturin develop
uv run task tests
uv run task build
```

Then install the built wheel in a clean environment and exercise at least one changed operation. For release changes, also build and install the generated sdist in isolation. Never weaken a check or coverage threshold to make a change pass; identify a repository-owned blocker instead.
